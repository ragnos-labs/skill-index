# Behavioral evaluation

Use synthetic briefs and included access/retrieval quotas. No separately metered
generation, account changes, public deployment, provider configuration changes,
or remote-host work. Preserve recoverable skill and registry snapshots before editing.

Keep builds, captures, nonsecret retrievals, and results outside the skill bundle
in one evaluation folder per run. Delete dependency folders and virtual
environments when the run closes; keep sources, captures and results. Record actual
host, model when observable, skill digest, tool calls, and outputs. Fresh workers
read the candidate instructions rather than inheriting producer conclusions.

## Host qualification

For each host independently:

1. Discover and resolve `design-kit` with the installed skill index.
2. Identify actual Mobbin, DesignMD, and 21st routes and perform real retrieval
   where supported. Configuration alone is not access. Preserve account scope.
3. Inspect a retrieved style/system/code resource, adapt it into a runnable
   output, and open the rendered pixels.
4. Record configured, callable, retrieved, inspected, used, and blocked stages
   per provider and host. Shared saved assets can support a build but do not
   substitute for that host's own live-provider qualification.

Use supported host CLIs or native agents. Bound subprocesses and keep logs/IDs.
Record access gaps once and continue independent work without repeated probes.

## Production briefs

Give builders the skill and brief without a prescribed implementation or visual
verdict. Give the fresh reviewer actual outputs before producer self-assessment.

### A. React operations screen

Build a fictional client-inquiry dashboard with request name, service, status,
received date, and next action. Include search/filtering, actionable detail,
responsive navigation, long content, and empty/loading/error states. Use a
new project that opts into the UI SDK the host has installed. Retrieve and inspect actual component source for a named gap, adapt suitable visual code to a coherent system, and
implement overlapping interaction behavior with SDK primitives. Inspect the
installed SDK documentation and test relevant user and agent actions. Keep
synthetic data local. Verify at 390, 768, and 1440 pixels; exercise keyboard, filters, detail
action, and states. Do not claim local demo actions send or save external records.

### B. Static service page

Build a fictional product-photography service landing page in semantic HTML/CSS
for small retail teams. Explain tabletop photography and prepare an inquiry.
Do not invent testimonials, clients, or outcome statistics. Use real retrieved
theme/system assets and inspected references, original or permitted imagery,
and an accessible inquiry interaction that sends nothing. No React dependency.
Verify all three widths.

### C. Three directions

For the same fictional service/content, build three rendered directions with
substantial differences in composition, hierarchy, imagery, or reading order.
Separate files/routes and equal-treatment comparison. Show desktop/mobile
evidence. Recommend from pixels; palette-only variants and fabricated sources fail.

### D. Campaign graphic

Create an editable fictional product-photography graphic with 1080x1350 and
1080x1080 PNGs. Exact copy: "Product photography" / "Clear images. Thoughtful
details." / "Studio sessions for small retail teams" / "Explore the session
guide". Use a coherent original product still-life or permitted asset. Recompose
the formats; keep text editable. Verify copy/dimensions and inspect full-size and
phone-size pixels. Link source and exports.

### E. Focused revision

Lengthen one content item and change one secondary action label in a completed
output. Preserve direction and unrelated behavior, reuse retrievals, and check
changed states visually/technically without forced redesign or new searches.

## Required-reads check

Run a first pass with no operator correction. From the transcript, confirm the
Director and the producer each read the files the entry file requires before
the first render or crop, and that the pack carried the kit digest and read
list. A read after production, or a host prompt to read, is a failed check.
Hand a producer a pack with no digest once and confirm it holds.

## Fresh-session probes

Run these three on each host after any change to the kit or to a role that
uses it. Each starts a fresh session with no operator correction, and each
passes or fails on what the transcript shows.

1. Director pack. Give the Director production brief B or D above. Pass: it
   returns a `design-pack.json` for which `design_pack.py check --kit-digest
   <the host's resolved digest>` exits 0, with the read list, brand block,
   `first_read`, a rejected alternative and `claims`.
2. Producer hold. Give the producer a pack with no kit digest, then one whose
   CMS learned record is marked not read. Pass: it holds both times, names the
   reason and makes nothing.
3. Critic on seeded defects. Keep one fixture render per host run with three
   planted defects and its pack in the evaluation folder: one blocking (for
   example required copy cut off by overflow), one major (a colored edge bar
   on a card, with edge bars named only as a house default in the review
   criteria, not as a success condition) and one minor that is unambiguous at
   full resolution (for example one block set 14 pixels off the shared left
   margin). State in the pack anything in the fixture that is intentional, so
   the critic does not grade the fixture's own shortcuts. Pass: it finds all three, grades
   each at its planted level, returns the verdict unmet, and reports no other
   blocking finding.

Record host, model, kit digest and the result of each probe in the evaluation
folder. A probe that needed a hint is a failed probe.

## Controlled failures

Exercise the combined Creative Director, Design Kit, builder, and UI SDK
pipeline when evaluating that integration: verify the builder received one
concise direction and an actual inspected design pack, the relevant installed SDK docs and project integration source
were inspected, interactions were implemented and tested, and mobile
and desktop pixels were opened. Include a real targeted retrieval, a rejected
asset with its reason, and a labeled fallback when a provider is unavailable.
Distinguish a live provider result from a simulated failure. Do not force a
provider call when evaluating an unrelated focused revision.

Use isolated response fixtures or supplied scenarios, never exhaust an account.
Label them as simulations. Exercise missing tools, quota refusal, unusable token
export, unsuitable component, and missing required brand/copy input. Expected
behavior: report the actual gap, stop the dependent branch, preserve project
architecture, use suitable alternatives, and never fabricate the missing input.
For equal foreground/background tokens, detect the defect, inspect underlying
specifications, and record the correction. Do not retry quotas or enable paid AI.

Judge observed behavior, not keyword matches. Simulations prove fallback handling
only, never live provider access.

## Acceptance and delivery

Require traceable retrieval-to-output use, inspected pixels, relevant technical
checks, faithful content, and concrete independent visual findings. Repair major
defects with matching-state evidence. Report provider/host coverage separately;
a good fallback output can coexist with an unqualified provider.

Validate frontmatter, links, and consistency; refresh registration through the
supported mechanism and resolve on each host. Review unrelated registry changes.
Report instruction validity, host execution, provider coverage, visual judgment,
and functional coverage separately. Local trials do not prove general or causal
quality improvements. Retain useful artifacts, close owned processes, and record
genuine blockers with next actions without introducing a scheduler.
